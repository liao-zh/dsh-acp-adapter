# 跨后端切换弹窗在源 provider 消失时无法关闭

- 记录日期：2026-11-15
- 状态：**bug 存在、未修**（等上游适配新 DSH 后切回上游，再复查一次）
- 版本：`@zaimokuza/dsh-acp-adapter` `0.2.2-rc.3.1`（本 fork `custom` 分支；profile 用 `link:` 装的就是它）
- 宿主：DSH 桌面版 `0.2.2-rc.3` / Windows 11
- 背景：上游还没适配 0.2.2，所以现在跑的是 fork。**这个 bug 的归属要等切回上游时再判定**——
  若上游同样存在，是我们的实现问题，需要提 issue；若上游已不存在，说明只是 fork 侧遗留。

## 一、症状

会话里把模型从非 ACP 的 provider 切到 ACP 路由时，弹出「需要新建会话」：

```
将从 <旧 provider> · <model> 切换到 acp-codebuddy-cli · <model>。
当前会话将保持不变，新的后端将在新 DSH 会话中运行。
⚠ 无法恢复当前会话原先使用的模型
```

- 「继续」是灰的（不可点）；
- 「取消」点了没反应，X 也一样；
- **重启 DSH 后自动回到同一会话，同一个弹窗再次出现**，等于这个会话打不开。

## 二、触发前提（两个都要满足）

1. 该会话**曾经**用一个非 ACP 的 provider（例如 providers-hub 提供的 `trae`）；
2. 之后这个 provider **消失**了 —— 插件被卸载、provider 未注册、账号被移除都算。

只满足其一不会走到死锁：源模型能恢复（或本来就没有）时，取消能正常关闭。

## 三、代码定位

| 位置 | 作用 |
|---|---|
| `src/client/coordinator/cross-backend-coordinator.ts` `stagePending()`（约 243–283） | 失败分支写 `failure.phase='restore-source'`、`confirmable: false`，**保留 pending** |
| 同上 `cancel()`（约 161–179） | 取消时先把 pending 置 `busy`，再调 `tx.cancel(...)`；结果非 ok 就把失败 pending 放回 |
| `src/client/data/cross-backend-controller.ts` `cancel()`（约 201–219） | `sourceAlreadyRestored !== true` 且存在 `sourceSelection` 时**再次** `restoreSource` → 同样的失败 |
| `src/client/ui/CrossBackendModal.ts`（约 45–88） | 「继续」`disabled = busy \|\| !confirmable`；「取消」与 X 都调 `coordinator.cancel()` |
| `src/client/ui/locales.ts`（约 399–411） | 文案来源，可用于全局搜索确认弹窗归属 |

链路：

1. 原生 picker 把 `next = acp route` 写进会话 `modelSelection`；
2. 协调器 `observe()` 判为跨后端 → `stagePending()` → `restoreSource(旧 provider)`；
3. 旧 provider 不存在 → `session.selectModel` 失败 → 挂起态 + `confirmable:false`；
4. 用户点取消 → `controller.cancel()` 再 `restoreSource` → 再失败 → pending 放回 ⇒ **无出口**；
5. 重启后会话的 `next` 仍是 ACP 路由，绑定即再次 `observe()`，`pending !== null` 又挡住重入 ⇒ 每次都卡在同一个弹窗。

要点：**「取消」在语义上依赖"恢复源模型成功"，而失败恰恰是源模型不可恢复**——
这是设计层面的循环依赖，不是偶发。

## 四、Agent 如何检查（复查清单）

### 4.1 静态判据（几十秒，改一次代码就能做）

在 fork 里看 `cancel()` 的失败分支是否仍然保留 pending、且没有任何清理路径：

```powershell
# 1) 失败分支是否仍然 confirmable:false 且保留 pending
Select-String -Path src\client\coordinator\cross-backend-coordinator.ts -Pattern "confirmable: false" -Context 2,6

# 2) cancel 里有没有 forget / 清空 pending 的兜底
Select-String -Path src\client\coordinator\cross-backend-coordinator.ts -Pattern "async cancel" -Context 0,25

# 3) controller 的 cancel 是否仍二次调用 restoreSource
Select-String -Path src\client\data\cross-backend-controller.ts -Pattern "async cancel" -Context 0,20
```

判据：**若 `cancel()` 里仍然只做「置 busy → restoreSource → 失败则放回 pending」，
且 `confirmable:false` 时没有「仅关闭」入口，bug 就还在。**

已修的样子（任一即可视为修复）：失败时 `tx.forget(ticket.key)` 并清空 pending；
或失败分支把 `confirmable` 置 true 并让主按钮变成「仅关闭」；或 `restoreSource` 失败时
回退到 `lastUsed` 且不再阻塞。

### 4.2 行为判据（可选，代价高，别在真实 profile 上做）

需要一个"源 provider 存在过又消失"的会话，真实环境很难造也容易搞坏会话。若确实要验：

1. 用隔离 profile（不要用 `desktop`），`dsh plugin --profile <临时名> ...` 起一个临时环境；
2. 会话先选一个**不存在的 provider id**（可在临时 profile 的 patch 里塞一个假 provider 行再删掉），
   制造"源模型不可恢复"；
3. 再切到 ACP 路由，看弹窗是否可关闭、重启后是否复现。

不满足这个前提时，弹窗行为是正常的（取消能关），**别把正常弹窗当成本 bug**。

## 五、严重度与影响

- **会话级死锁**：那个会话在 UI 上打不开，「继续」不可用；改不了模型也关不掉弹窗。
- **不损坏数据**：会话历史仍在 `~/.dsh/sessions/...jsonl.zst`，换 profile 或禁用插件后可以正常打开。
- 影响面限于"源 provider 已消失 + 用户还想去点 ACP 模型"这一组合；正常升级不会触发。

## 六、临时规避（按代价排序）

1. 把源 provider 装回来、账号可用 → `restoreSource` 成功 → 点「取消」即可正常关闭。
2. 临时禁用适配器启动一次：profile `cordis.patch.yml` 加 `- id: dsh-acp-adapter` + `disabled: true`，
   进去把会话模型选回可用 provider（或归档会话），再删掉这条。
3. 换一个 profile 启动，进去再切回来（实测有效）。
4. 改会话数据：**不建议**，会话是 zstd 压缩的 `session.v4.jsonl.zst`。

## 七、不修的理由

fork 的定位是"等上游适配后切回上游"（见 `notes/README.md` 的「切回上游」）。
在这里动协调器等于给一个即将被替换的分支加维护面，且修法牵涉跨后端事务语义，
需要配套测试；收益低于成本。**只要上游修了，这条就不必做。**

若期间再次遇到同类卡死，按第六节规避，不要临时改 `lib/`（重装即丢，且 `lib/` 不进 `custom`）。

### Title（English）

```
Cross-backend switch modal cannot be dismissed when the source model's provider is gone
```

### Body（English）

```markdown
### Summary
When a session's last-used provider is no longer registered, picking an ACP model
opens the "new session required" modal in a permanently failed state: Continue is
disabled and Cancel re-runs the same failing restore, so the modal cannot be closed —
not even by restarting the app.

### Environment
- DSH 0.2.2-rc.3 (Desktop, Windows 11)
- @zaimokuza/dsh-acp-adapter <version under test>

### Steps to reproduce
1. Use a session with history on a non-ACP provider X (e.g. `trae`).
2. Make X unavailable — e.g. remove the plugin that registers it.
3. In that session, select an ACP model.
4. Modal shows a `restore-source` failure; Continue is disabled; Cancel does nothing.
5. Restart DSH: the app reopens the same session and the same modal appears.

### Expected
Cancel must always be able to abandon the transition (best effort: revert to
`lastUsed`, otherwise leave the selection as-is with a warning). If the transition
cannot proceed, say what the user can do instead.

### Cause (code)
- `CrossBackendCoordinator.stagePending`: on `restoreSource` failure → `confirmable: false`,
  and `pending` is kept.
- `CrossBackendCoordinator.cancel` → `CrossBackendTransactionController.cancel` →
  `operations.restoreSource` again → fails again → coordinator restores the same failed
  `pending`. No branch clears it.
- The session's `modelSelection.next` stays on the ACP route, so every rebind
  re-observes the cross-backend transition on startup.

### Suggested fix
In `cancel()`, when `restoreSource` fails, `tx.forget(key)` and clear `pending`
(or expose an explicit dismiss action while `confirmable === false`).

### Workaround
Disable the adapter for one boot, or start with another profile, then fix the
session's model selection.
```

```markdown
### 概述
当会话上次使用的 provider 已不存在时，选择一个 ACP 模型会打开「需要新建会话」弹窗，
并卡在失败态：「继续」被禁用，「取消」重跑同一个必然失败的恢复流程，弹窗关不掉，
重启 DSH 后依旧。

### 环境
- DSH 0.2.2-rc.3（桌面版，Windows 11）
- @zaimokuza/dsh-acp-adapter <被测版本>

### 复现步骤
1. 一个有历史的会话，上次使用的是非 ACP 的 provider X（例如 `trae`）；
2. 让 X 不可用 —— 例如卸载注册它的插件；
3. 在该会话里选择一个 ACP 模型；
4. 弹窗显示 `restore-source` 失败；「继续」为灰；「取消」无任何反应；
5. 重启 DSH：自动回到同一会话，同一弹窗再次出现。

### 期望行为
「取消」在任何情况下都应能放弃本次切换（尽量回退到 `lastUsed`；退不回去就保留当前选择
并给出提示）。若切换无法进行，应说明用户还能怎么做。

### 原因（代码层面）
- `CrossBackendCoordinator.stagePending`：`restoreSource` 失败 → `confirmable: false`，
  且 `pending` 被保留；
- `CrossBackendCoordinator.cancel` → `CrossBackendTransactionController.cancel` →
  再次调用 `operations.restoreSource` → 再次失败 → 协调器把同一个失败的 `pending` 放回，
  没有任何分支清理它；
- 会话的 `modelSelection.next` 仍指向 ACP 路由，所以每次重新绑定都会在启动时再次判定为
  跨后端切换。

### 建议修法
在 `cancel()` 中，若 `restoreSource` 失败，则 `tx.forget(key)` 并清空 `pending`；
或在 `confirmable === false` 时提供显式的「仅关闭」操作。

### 临时规避
临时禁用适配器启动一次，或换一个 profile 启动，再把会话的模型选择改回来。
```
