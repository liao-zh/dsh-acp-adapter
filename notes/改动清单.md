### 2026-11-13 适配 DSH 0.2.2-rc.3

- 类型：适配
- 文件：`package.json`（122 条依赖版本 + `version` + `engines.dsh`）、`pnpm-lock.yaml`（重装产生）、`notes/README.md`（示例产物名与体检命令的版本号）
- 为什么：门禁 `plugin-compatibility.ts` 判 `semver.satisfies(runtime, engines.dsh, { includePrerelease: true })`。适配器原 `engines.dsh = 0.2.2-rc.2` 是**精确版本**，在 rc.3 上不满足 ⇒ bundle 级直接 `throw`（`app-boot/src/profile.ts` 的 `evaluatePluginCompatibility`），适配器整行被跳过。
- 上游状态：**不适用**（上游仍停在 0.2.1-rc.4.1）
- 可丢弃：否（丢弃后插件在 rc.3 上不加载）

改动明细：

| 处 | 原文 | 新文 | 数量 |
|---|---|---|---|
| `version` | `0.2.2-rc.2.2` | `0.2.2-rc.3.1` | 1 |
| `engines.dsh` | `0.2.2-rc.2` | `0.2.2-rc.3` | 1 |
| `peerDependencies` 的 `@deepseek-ai/dsh*` | `0.2.2-rc.2` | `0.2.2-rc.3` | 40 |
| `devDependencies` 的 `@deepseek-ai/dsh*` | `0.2.2-rc.2` | `0.2.2-rc.3` | 82 |

**没有改代的同族包**（rc.3 宿主声明未变，动了会引发 pnpm 双实例，见「已知遗留」）：
`@deepseek-ai/cordis 4.1.0`、`cordis-plugin-group 1.1.0`、`cordis-plugin-loader 1.1.0`、
`@deepseek-ai/schemastery 3.19.0`、`zod 4.6.6`、`react`/`react-dom 18.3.1`。

**为什么选精确版本而不是范围**：`>=0.2.2-rc.2 <0.2.3` 会放进 `0.2.3-rc.1`（下个 minor 的预发布版，
已用仓库内 semver 实测），要开区间须写 `<0.2.3-0`。而 `engines.dsh` 一旦成范围，
`scripts/dsh-target.ts` 的「精确版本」正则、`verify-bundle.ts` 的 4 处相等断言、
`check-fork-state.ts` 的 2 处比较、以及 2 个测试都要跟着改；且 `devDependencies`
只能钉一个精确版本，rc.2 那条腿永远验证不到 —— 声明了却验不了的兼容会掩盖真不兼容。

#### 遗留噪音：`dsh-error` 被解析成 rc.2（已验证无影响）

`pnpm install` 之后，`.pnpm` 里 `@deepseek-ai/dsh-error` 只有 **rc.2** 一个实例，而全图 202 个包
都在 `peerDependencies` 里要求 `0.2.2-rc.3`，`pnpm install` 每次都打印一串
`✕ unmet peer @deepseek-ai/dsh-error@0.2.2-rc.3: found 0.2.2-rc.2`。

排查过的路子（都排除）：删 `pnpm-lock.yaml` 重装、`pnpm install --force`、`pnpm store prune`
（清了 4245 个文件 / 89 个包）、`pnpm dedupe` 都不是根因；隔离的空项目里
`dsh-llm@rc.3` 能正确解析出 `dsh-error@rc.3`。它是本仓库依赖图内某种 peer 合并的结果。

**判断为可接受**：两版 tarball 解包对比，除 `package/package.json` 的 `version` 字段外
**10 个文件全部逐字节相同**，`lib/index.js` 哈希一致 ⇒ 不存在 `HarnessError` 类双实现、
`instanceof` 也不会跨实现失效。

⚠️ **下次升级时这里会重新出现**，别把它当成新回归；也不要为此加 `pnpm.overrides`
（那会把上游的 peer 契约硬钉住，将来真升级时更难查）。若哪天 `dsh-error` 两版真有
代码差异，`pnpm why @deepseek-ai/dsh-error` 是第一诊断入口。

### 2026-11-12 适配 DSH 0.2.2-rc.2（提交 6dc3715）

- 类型：适配
- 文件：`package.json`、`src/`（29 个文件）、删除 9 个文件
- 为什么：DSH 0.2.1-rc.4 → 0.2.2-rc.2 有 20+ 处破坏性变更，插件激活即报
  `ctx.get(...)?.tryMembership is not a function`。
- 上游状态：**未修**（上游 0.2.1-rc.4.1 停在 10-28，无 0.2.2 兼容版）
- 可丢弃：否（丢弃后插件在 0.2.2 上无法启动）

主要变更：

| 根因 | 处数 | 处理 |
|---|---|---|
| `LlmError` 构造器只收内置 code | 92 | 全部改 `LlmError.fromFailure({ message, code })` |
| `tools.execute` 单次 → 批次 `ToolBatchInput` | 1 | `calls:[{type:'tool-call', id, name, arguments: JSON.stringify(args)}]`，结果取 `batch.results[0]`，`additionalContexts` 合并 |
| `tools.executionMode` 删除 | 1 | 改用 `definition.isConcurrencySafe` |
| `agentTeams` roster 整套删除 | 22 | `tryMembership`/`listMembers` → `subagents.rootOf` / `namesOf` / `isEnabled` |
| `stateOf(session, key)` 废弃（返回 unknown） | 10 | 自注册单元走 `ProjectionHandle.stateOf`；宿主单元走 `snapshot().values` |
| `register()` 变异步返回 handle | 2 | 捕获 handle 后读取 |
| `agents.roots()` / `isOwnedBy()` 删除 | 6 | `subagents.rootOf` + `parentSession` 重建 |
| `ProjectionDefinition` 需 2 个泛型参数 | 2 | 补状态类型 |
| zod 4.4.3 与宿主 4.6.6 双实例 | — | 升到 4.6.6 |
| `modelSelection.pending` → `next` | 1 | 字段改名 |
| `title` 投影删除 | 1 | 改用 `useSessions` 的 `SessionListEntry.title` |
| `subagents/interruptByParent` → `interruptByUser` | 2 | 端点改名，参数 3 → 1 |
| `getAnchorRect` → `anchor` 元素（CSS 锚点） | 2 | 删除测量回调 |
| `NativeOwner.fileMentions` 删除 | 2 | 删字段 |
| `PermissionSelection` 结构变 `{currentValue}` | 1 | 对齐 |
| `files` 缺 `lib/typert.remote-client.d.ts.map` 校验 | 1 | 补进 `package.json` |

删除的文件（能力在 0.2.2 中整体消失，无数据源）：
`host/teams/{management,member-models,member-model-tools,member-model-facts}.ts`、
`client/ui/{AcpTeamManagement,TeamMemberModelControl}.ts` 及 3 个测试。

功能影响：
- 保留：ACP 会话、工具桥、subagent、审批、诊断、`team_task_*` 任务板
- 降级：Team 成员面板不挂载（`TeamProjection` 只剩 `enabled`/`tasks`/`failure`）
